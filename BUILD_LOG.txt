v1.2.0 — COMPETITION FOUNDATION (CONFIGS, SESSIONS, RESULTS, VALIDATION STATE)
=====================================
Status: IMPLEMENTED for PRACTICE; PAID modelled but DISABLED. Typecheck, unit,
mocked-integration, real-PostgreSQL and production-build checks pass. Migration 0004
NOT yet applied to the real Supabase project; nothing verified on Supabase/Vercel.
Versioning: MAJOR.MINOR.PATCH from here on (new capability = minor bump).

Implemented:
- Competition configurations (data, not code): game, format (SCORE_ATTACK /
  ONE_V_ONE), mode PRACTICE | PAID, integer PlayCoin entry fee, reward model
  FIXED | PRIZE_POOL with parameters, enabled flag, timestamps. Any number of
  tiers per game+format; no tier names or prices in code. Practice = fee 0 and no
  reward; paid = fee > 0 + a valid reward config. Terms immutable once created.
- Sessions: config, game, format, mode, status, validation status, settlement
  status, created/started/deadline/completed/validated/settled timestamps.
  Status: WAITING (1v1 only) -> READY -> IN_PROGRESS -> COMPLETED (practice) |
  SUBMITTED -> COMPLETED (paid, after validator); WAITING/READY -> CANCELLED;
  IN_PROGRESS -> ABANDONED (quit or deadline + 30s grace passed).
- Participants: exactly 1 (SCORE_ATTACK) or 2 (ONE_V_ONE), no duplicates. Both
  1v1 players share the session's single config, so they are on the same tier.
- Results: one immutable result per session. SCORE_ATTACK: integer score
  0..1e12. ONE_V_ONE: winner slot or draw. Never trusted: practice -> UNVERIFIED;
  paid -> PENDING until a trusted validator (service_role) records VERIFIED or
  REJECTED, exactly once.
- Settlement TRACKING only: NOT_REQUIRED (practice) or PENDING -> COMPLETED,
  once, only for terminal sessions. src/lib/competitions/settlement.ts PLANS
  payouts (fixed reward, 1v1 prize pool with integer fee rounding, draw/cancel
  refunds, deterministic ledger references for idempotency) but executes nothing.
- Server operations (src/server/competitions.ts) + API routes:
  GET  /api/competitions/configs?gameId=&format=
  POST /api/competitions/sessions {configId}
  GET  /api/competitions/sessions/:id
  POST /api/competitions/sessions/:id/{join,start,cancel} {}
  POST /api/competitions/sessions/:id/result {format, score | winnerSlot}
  Trusted validator: src/server/competition-validation.ts (service role, NO route).
- Game SDK: manifest `formats` (replaces type/minPlayers/maxPlayers/
  durationSeconds, which were platform-owned anyway); competition contract
  (statuses, CompetitionOption, SessionView, resultSubmissionSchema,
  GamePlatformApi interface with no wallet/settlement methods). Removed unused
  MATCH_STATES. GameCard shows format badges.

Migration 0004 (additive, one transaction):
- Creates 4 tables, guard triggers, 2 deferred participant-count constraint
  triggers, RLS policies, grants and functions. Does not alter, drop or reset
  0001-0003 objects or data. Applied ONLY to local test databases so far.
- Behaviour note: users with competition history cannot be hard-deleted
  (on delete restrict), the same rule wallet_transactions already applies.

Security:
- Identity only from the verified session (requireUser) and auth.uid() in SQL;
  no route or RPC accepts a user id; strict zod bodies reject extra fields.
- Players: SELECT only, and only rows of sessions they participate in (RLS).
  All writes go through SECURITY DEFINER functions (search_path=''), which lock
  the player's profile row (serialises per-player ops) and the session row.
  Non-participants get session_not_found (no information leak).
- Guard triggers enforce transitions, immutable identity/terms/history,
  immutable participants/results and one-time validation/settlement for EVERY
  role, including service_role. EXECUTE revoked from PUBLIC/anon/authenticated
  on all internal functions (Supabase default privileges grant it otherwise).
- Abuse guards: max 3 open sessions per player (race-safe), deadlines.
- Mutating routes require application/json (blocks cross-site form posts).
- Games/SDK cannot import server, Supabase or wallet code (static test).
- Service-role client used only by the validator module; not in any bundle.
